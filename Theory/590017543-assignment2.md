## Part A: Conceptual Questions

### Q1. What is `jsonb` in PostgreSQL, and how does it differ from the plain `json` type?

Both types store JSON data and both reject invalid JSON, but they store it very differently.

**`json`** stores an exact text copy of the input. Spaces, key order and even duplicate keys are kept as they were typed. Because it is only text, PostgreSQL has to parse it again every time a query reads a key.

**`jsonb`** ("JSON binary") parses the input once, at insert time, and stores it in a decomposed binary format. Extra spaces are removed, keys are stored in its own order, and if a key appears twice only the last value is kept.

```sql
SELECT '{"b": 1, "a": 2, "a": 3}'::json  AS as_json,
       '{"b": 1, "a": 2, "a": 3}'::jsonb AS as_jsonb;
--          as_json          |     as_jsonb
--  {"b": 1, "a": 2, "a": 3} | {"a": 3, "b": 1}
```

**Effect on write speed:** `jsonb` writes are slower because every value must be converted. Inserting 300,000 documents took about 440 to 510 ms as `json` and about 800 ms as `jsonb`.

**Effect on query and index speed:** `jsonb` reads are faster because nothing is re-parsed. The same lookup on `pages` took about 103 ms on `json` and about 40 ms on `jsonb`. Only `jsonb` supports GIN indexes and operators such as `@>`, `?` and `=`.

**Storage size:** `jsonb` is not always smaller. In my test the `jsonb` table was 33 MB against 29 MB for `json`.

In practice, `jsonb` is the right choice almost always. `json` is useful only when the exact original text must be preserved.

### Q2. How can PostgreSQL work as both a SQL and a NoSQL database in the same table?

A single table can mix two kinds of columns:

1. **Strictly typed columns** for data that every row has, such as `id`, `name`, `category` and `price`. These get full relational rules: data types, `NOT NULL`, `UNIQUE`, `CHECK` and foreign keys. This is the "SQL" part.
2. **One `jsonb` column** for data that changes from row to row. In a product catalog, a book has `author` and `pages`, a laptop has `ram_gb` and `cpu`, and a mouse has `color` and `wireless`. Creating a separate column for every possible attribute would leave most cells NULL, and adding a new category would need `ALTER TABLE`. Inside `jsonb`, each row can have its own set of keys. This is the "NoSQL" (document) part.

```sql
CREATE TABLE products (
    id         INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       VARCHAR(100)  NOT NULL,
    category   VARCHAR(50)   NOT NULL,
    price      NUMERIC(10,2) NOT NULL CHECK (price >= 0),
    attributes JSONB          -- flexible, per-category attributes
);
```

One query can then use both parts together, with normal SQL filtering on fixed columns and document filtering on the `jsonb` column:

```sql
SELECT name, price, attributes ->> 'cpu' AS cpu
FROM products
WHERE category = 'laptop'                    -- relational filter
  AND (attributes ->> 'ram_gb')::int >= 16;  -- document filter
```

So the stable, important fields keep strong guarantees, while the changing fields stay flexible, all in one table, one transaction and one database.

### Q3. Examples of `jsonb` queries using `->`, `->>`, `@>` and `?`

All examples use the `products` table from Part B.

| Operator | Meaning | Query | Value returned |
|---|---|---|---|
| `->` | Get a key, result stays **`jsonb`** | `SELECT attributes -> 'author' FROM products WHERE name = 'Clean Code';` | `"Robert C. Martin"` (with quotes, type `jsonb`) |
| `->>` | Get a key, result is **`text`** | `SELECT attributes ->> 'author' FROM products WHERE name = 'Clean Code';` | `Robert C. Martin` (no quotes, type `text`) |
| `@>` | Left value **contains** the right JSON | `SELECT name FROM products WHERE attributes @> '{"cpu": "Apple M3"}';` | `MacBook Air M3` |
| `?` | **Key exists** at the top level | `SELECT name FROM products WHERE attributes ? 'author';` | `Clean Code`, `The Pragmatic Programmer` |

**Difference between `->` and `->>`:** both read a key, but the type of the result is different. I checked it with `pg_typeof()`:

```sql
SELECT pg_typeof(attributes -> 'pages')  AS type1,
       pg_typeof(attributes ->> 'pages') AS type2
FROM products WHERE name = 'Clean Code';
--  type1 | type2
--  jsonb | text
```

- Use `->` when you need to go deeper into the JSON, because the result is still JSON and can be chained: `attributes -> 'address' ->> 'city'`.
- Use `->>` for the final value, when you want to compare, display or cast it: `(attributes ->> 'pages')::int > 400`. Comparing with `->` would compare JSON values, not plain text or numbers.

### Q4. How can a GIN index on a `jsonb` column change query performance?

A **GIN (Generalized Inverted Index)** works like the index at the back of a book. Instead of one entry per row, it stores every key and value found inside the documents, and for each one, the list of rows that contain it. To answer "which rows contain `"wireless": true`?", PostgreSQL looks up that entry directly instead of opening every row.

```sql
CREATE INDEX idx_products_attributes ON products USING GIN (attributes);
```

**What it speeds up:** containment and key-existence operators: `@>`, `?`, `?|` and `?&`. On a table with 200,000 rows:

```sql
SELECT name FROM products_big WHERE attributes @> '{"wireless": true}';
-- Before index: Seq Scan,                       41.49 ms
-- After index:  Bitmap Index Scan (GIN index),   0.38 ms   (about 110x faster)
```

**What it does not help with:** extracting a value with `->>` and comparing it, especially range comparisons:

```sql
SELECT name FROM products_big
WHERE category = 'laptop' AND (attributes ->> 'ram_gb')::int >= 16;
-- Before index: Seq Scan, 26.94 ms
-- After index:  Seq Scan, 30.59 ms   (index not used)
```

The GIN index only knows which documents contain a key and value pair, not the order of the numbers. For this kind of query, a B-tree **expression index** is needed, for example `CREATE INDEX ON products_big (((attributes ->> 'ram_gb')::int));`.

Two other points from testing: on the 5-row table the planner ignored the index completely, because reading 5 rows directly is cheaper. And an index has costs: it used 1.7 MB of extra space for a 20 MB table, and it makes every insert and update a little slower.

### Q5. Where could PostgreSQL + `jsonb` replace MongoDB, and where would MongoDB still be the better fit?

**Transactions.** PostgreSQL gives full ACID transactions across any number of rows and tables, for example reducing stock and creating an order in one step. MongoDB has supported multi-document transactions since version 4.0, but its design is centered on single-document operations, and transactions add extra cost. **Advantage: PostgreSQL.**

**Joins.** In PostgreSQL, a `jsonb` row can be joined normally with other tables:

```sql
SELECT o.id, p.name, p.attributes ->> 'cpu' AS cpu
FROM orders o JOIN products p ON p.id = o.product_id;
```

MongoDB uses `$lookup` in an aggregation pipeline, which is more limited and more verbose. **Advantage: PostgreSQL.**

**Schema enforcement.** PostgreSQL enforces types, `NOT NULL`, `CHECK` and foreign keys on fixed columns and can also add `CHECK` rules on the `jsonb` data. MongoDB is schema-less by default, and validation (`$jsonSchema`) is optional. **Advantage: PostgreSQL for safety, MongoDB for freedom to change quickly.**

**Horizontal scaling.** MongoDB has built-in sharding and replica sets, so data can be spread over many servers as it grows. PostgreSQL mainly scales vertically, and splitting writes across many servers needs extensions such as Citus or manual partitioning. **Advantage: MongoDB.**

**Conclusion:** PostgreSQL + `jsonb` can replace MongoDB when data is mostly relational with some flexible attributes (product catalogs, user settings, e-commerce) and needs transactions and joins. MongoDB is still the better fit for very large, write-heavy, document-only workloads that need automatic sharding across many servers, such as logs, IoT readings or chat messages.

**Conclusions from Task 6:**

1. A GIN index makes `@>` (and `?`) queries dramatically faster on large tables.
2. A GIN index does not help `->>` value comparisons. Those need a B-tree expression index on the extracted value.
3. On very small tables, PostgreSQL correctly ignores indexes, so `EXPLAIN ANALYZE` on tiny test data cannot show the benefit.
4. Indexes cost extra disk space and slow down writes, so they should only be created for queries that are actually used often.

#### Differences Noticed

| Point | PostgreSQL + `jsonb` | MongoDB |
|---|---|---|
| **Syntax** | SQL with JSON operators: `->>`, `@>`, `?`, `\|\|` | JavaScript-style objects: dot paths (`"attributes.ram_gb"`) and `$` operators (`$gt`, `$exists`, `$set`) |
| **Numbers** | `->>` returns text, so a cast is required: `(attributes ->> 'ram_gb')::int >= 16` | Numbers stay numbers: `{ "attributes.ram_gb": { $gte: 16 } }`, no cast |
| **Insert** | JSON written as a string inside SQL, typed columns checked | Plain JavaScript objects, no table to create first |
| **Schema** | Fixed columns enforced (`NOT NULL`, types), only `attributes` is flexible | No schema by default; any document shape is accepted |
| **Adding a field** | `attributes \|\| '{"discount_pct": 10}'` | `$set: { "attributes.discount_pct": 10 }` |
| **Indexing** | One GIN index covers containment on **all** keys; range queries need a separate expression index | Index is created **per field path** (`{"attributes.ram_gb": 1}`) and supports both equality and range |
| **Ease of use** | More typing (casts, quotes), but one language for relational and document data, plus joins and transactions | Shorter and more natural for nested data; joins require `$lookup` |

**Overall:** for this product catalog, both databases handled the varying attributes well. MongoDB was easier for nested queries because numbers did not need casting. PostgreSQL needed slightly more syntax, but kept strict rules on the fixed columns and can join products with other tables (orders, users) in one query, which matters for an e-commerce system.
